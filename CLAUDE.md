# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A ROS 2 Humble competition robot (RDK X5 / Ubuntu 22.04), plus a WPF desktop companion app
and the provisioning/streaming services that run beside ROS on the robot. The repo *is* the
colcon workspace source tree — on the robot it is cloned to `~/risabotcar_ws`, so `src/`
here is `~/risabotcar_ws/src`.

Development happens on a Windows PC. The split matters:

- **The ROS 2 side (`src/`) does not build or run locally.** Every build, test and launch
  happens over SSH on the robot. Treat edits as source changes to be deployed, not as
  something you can verify in-process.
- **`RisaBotApp/` does build and run locally** — it is a Windows desktop app, so `dotnet
  build` and launching the exe are both fair game on the PC. It only needs the robot when
  it wants live data.
- **`tools/wifi_provisioning/backend/app.py` can be exercised locally without the robot**
  by importing it with `fastapi` stubbed out and driving its handlers from a stdlib HTTP
  server. That is how the model endpoints were tested; see the note on that file below.

## Branches

| Branch | Purpose | Launch |
| --- | --- | --- |
| `main` | Individual node testing; **all documentation lives here** | `run_risabot` |
| `test` | Competition mode, monolithic | `ros2 launch risabot_automode competition.launch.py` |
| `refactor-test` | Competition mode, refactored + dashboard + app | `ros2 launch risabot_automode bringup.launch.py` |

Doc changes go on `main` only. Three remotes exist — push to `origin`
(`eemrull/RISA-bot`). Do not push to `company` or `company-challenge`.

One caveat to that rule: the companion app and the dashboard only exist on `refactor-test`,
so documentation *about them* (including the app sections of this file) is necessarily edited
there. Don't try to reconcile it onto `main` — `main` has no `RisaBotApp/` to describe.

## Build / run / deploy

All on the robot, over SSH:

```bash
cd ~/risabotcar_ws/src/RISA-bot && git pull   # only from inside the package dir
cd ~/risabotcar_ws && cb && sos               # full rebuild + re-source
cbp risabot_automode                          # rebuild one package (fastest)
cbc                                           # clean rebuild of the two Python packages
ros2 launch risabot_automode bringup.launch.py
```

Aliases (`cb`, `cbp`, `cbc`, `sos`, `run_risabot`, …) are generated by
`tools/install_bashalias.sh`; the definitive list is in that script.

**Editing a Python node is not enough.** `install/` holds the copy that actually runs, so
after any Python change run `colcon build --packages-select <pkg>` — an scp of the source
file changes nothing. (`--symlink-install` is used, but the install tree still has to be
regenerated for new/renamed files and entry points.)

`ros2_astra_camera` and `ydlidar_ros2_driver` carry a `COLCON_IGNORE` after the first
successful build so C++ isn't recompiled; remove it if you touch their sources.

`tools/deploy_to_robots_paramiko.py` and `tools/bulk_setup_robots.py` drive several robots
at once over paramiko (model upload, git pull, build, verify).

### Tests

Only ament boilerplate (`test_flake8.py`, `test_pep257.py`, `test_copyright.py`) per package
— there are no behavioural unit tests. Run on the robot:

```bash
cd ~/risabotcar_ws && colcon test --packages-select risabot_automode && colcon test-result --verbose
pytest src/risabot_automode/test/test_flake8.py    # single test
```

Real verification is on hardware. `src/risabot_automode/risabot_automode/bag_regression_validator.py`
replays bags against nodes; `tools/bpu_model/verify_live.py` checks the YOLO BPU path.

### Companion app

Locally, on the PC — this one is not deployed anywhere:

```powershell
cd RisaBotApp
dotnet build RisaBotApp.csproj
.\bin\Debug\net10.0-windows\RisaBotApp.exe
```

**No `-f` flag.** The app was rewritten from .NET MAUI to WPF and now has a single
`TargetFramework` (`net10.0-windows`), so passing `-f net10.0-windows10.0.19041.0` or
`-f net10.0-android` fails with NETSDK1005 — those target frameworks no longer exist. The
MAUI multi-target build and the Android head are both retired; the Android head had never
been compiled and every operator runs Windows.

Dependencies are just `CommunityToolkit.Mvvm` 8.4.0 (MVVM source generators) and
`Microsoft.Extensions.DependencyInjection` 10.0.0. There is no MAUI workload to match
any more.

**If the build fails with MSB3027/MSB3021 "file is locked by",** a copy of the app is still
running and holding `bin\Debug\net10.0-windows\RisaBotApp.exe`. Trust the PID in that error
message and stop it — `Get-Process RisaBotApp` has been observed returning nothing while the
process demonstrably exists.

## Architecture

### The control chain

Perception nodes publish *facts* (booleans, errors, or a candidate `cmd_vel`); `auto_driver`
is the only node that decides. It runs a priority-ordered state machine on a 50 Hz timer
(`cmd_vel_timer`, 0.02 s) and picks exactly one behaviour per tick.

```
sensors → perception nodes → auto_driver (ChallengeState) → /cmd_vel_auto_raw
        → cmd_safety_controller → /cmd_vel_auto → servo_controller → Rosmaster_Lib (serial)
```

`ChallengeState` (`auto_driver.py:63`) enumerates the 17 states. Priority order and triggers
are tabulated in `ARCHITECTURE.md`; the full node/topic graph is there too. Behaviours that
need their own motion (tunnel, obstruction, parking) publish a *suggested* velocity on their
own topic (`/tunnel_cmd_vel`, `/obstruction_cmd_vel`, `/parking_cmd_vel`) and `auto_driver`
forwards it only while that state is active. Adding a behaviour means adding a state and a
priority slot, not a new publisher to `/cmd_vel`.

`cmd_safety_controller` sits between brain and hardware and enforces limits and e-stop —
never bypass it by publishing to `/cmd_vel_auto` directly.

`servo_controller` (`control_servo`) owns the serial link to the motor board and is also the
source of `/odom`, `/imu/pitch`, `/auto_mode` and `/set_challenge` — the joystick reaches
the state machine through it, not directly.

Topic names are constants in `src/risabot_automode/risabot_automode/topics.py` (and a smaller
`control_servo/topics.py`). Use them; don't hardcode strings.

### Parameters

`src/risabot_automode/config/params.yaml` is the single source of tuning truth — one block
per node name, loaded by every launch file. Node names in that file must match the `name=`
in the launch file or the parameters silently don't apply. `ros2 param get` intermittently
fails with `!rclpy.ok()`; read the YAML instead of fighting it.

### Perception

Camera lane detection (`line_follower_camera.py`) is scanline-based and vectorised — it runs
at ~31 Hz against a 30 Hz camera. Keep per-pixel Python loops out of its hot path.

`signage_detector.py` runs a custom YOLOv5s on the RDK X5 BPU via `hobot_dnn`/`pyeasy_dnn`
(NV12 input, 640×640, INT8). The model is compiled offline on a PC — dataset → Colab training
→ ONNX → `patch_onnx_resize.py` → `hb_mapper` in Docker → `.bin` scp'd to the robot. Toolchain
and config live in `tools/bpu_model/`; the flow is diagrammed in `ARCHITECTURE.md`.

### Services on the robot (four listeners, four ports)

| Port | Service | Provided by |
| --- | --- | --- |
| 8000 | Provisioning portal / launch control (FastAPI+uvicorn) | `tools/wifi_provisioning/backend/app.py` |
| 8080 | ROS web dashboard (stdlib HTTP, 20 endpoints) | `dashboard.py` + `dashboard_templates.py` |
| 1984 | go2rtc — what browsers and the app consume | `tools/go2rtc/` |
| 1985 | MJPEG source that go2rtc pulls from | `ros2go2rtc_bridge.py` |

The camera chain is ROS topic → bridge `:1985` → go2rtc `:1984` → client. Two things silently
break it: go2rtc's stream URL must use the plain `http` scheme (there is no `mjpeg:` scheme),
and the client must hit `/api/stream.mjpeg`, not go2rtc's `stream.html` player page.

Camera view switching goes through `/api/set_cam_view?view=…` on 8080, which sets
`active_view` on the bridge *and* toggles `show_debug` on the matching perception node. Valid
views are `raw`, `line_follower`, `obstacle`, `signage`, `traffic_light` — the handler returns
200 for anything, so an invalid name fails silently and blanks all debug overlays.

Port 8000 also serves AI-model management, used by the app's Settings page:
`GET /api/model/info` (name/size/mtime/sha256 of the installed `.bin`),
`POST /api/model/upload` (streamed to a temp file, validated, then atomically swapped in,
keeping the previous model as `.bak`) and `POST /api/model/rollback`. The model lives at
`/home/sunrise/risabot_signs_640x640_nv12.bin` — outside the colcon workspace — and the
portal runs as root while `risabot.service` runs as `sunrise`, so an uploaded file has to be
`chown`ed. Upload validates the BPU `.bin` magic (protobuf starting `08 01 10 01 2a`) and
rejects a mistakenly-uploaded ONNX or zip by inspecting byte 2.

**`app.py` is not run from the repo.** `risabot-wifi-portal.service` sets
`WorkingDirectory=/etc/risabot/portal/backend` and uvicorn imports the copy there, so a `git
pull` alone changes nothing — new endpoints just stay 404. Copy it over, `ast.parse` it, then
restart; the file's own module docstring carries the exact command sequence and the reason to
keep a `.bak` (uvicorn dies on an import error, and the portal is the only channel you would
use to fix it).

The systemd units are `risabot`, `go2rtc`, `risabot-wifi-portal`, `risabot-hostapd`,
`risabot-dnsmasq`, `risabot-ap-interface`. `setup_autostart.sh` installs `risabot.service`
**disabled** — the app starts it via `POST /api/launch_start`. If it is running, `ros2 launch`
by hand collides on ports 8080 and 1985: `sudo systemctl stop risabot` first.

### Companion app (`RisaBotApp/`)

WPF, MVVM with CommunityToolkit.Mvvm. Services and view-models are registered in
`App.OnStartup` (`App.xaml.cs`) — the composition root, replacing MAUI's `MauiProgram.cs`.

Navigation is not a framework feature: the window body is a `ContentControl` and
`NavigationService` swaps the view in it, driven by the `Route` enum
(`Services/NavigationService.cs`) — `Splash, Discovery, WifiSetup, Dashboard, Controls,
Logs, DataLogger, Slam, Settings`. Adding a screen means a `Route` member, a view, and a case
in the navigation switch — plus an entry in **both** nav panels in `MainWindow.xaml`, the
horizontal `GroupName="TopNav"` bar and the `GroupName="DrawerNav"` drawer, which are
separate `RadioButton` groups and are easy to update only one of.

Startup always lands on Discovery, even with a robot remembered. That is deliberate and
documented in `MainViewModel.StartAsync`: a remembered pairing is a default, not a decision,
and several robots may be on the bench.

`ApiClient.cs` is the one place that knows about ports: it derives the 8080 and 1984 base
URLs from whatever host the portal (8000) was reached on.

**`ApiClient` has two HttpClients, and the distinction is load-bearing.** The DI singleton
has `Timeout = 10 s`, which is a hard ceiling that no per-request `CancellationTokenSource`
can raise — a `CancelAfter(90_000)` on a request issued through it still gives up at 10 s.
Anything slower than 10 s must go through the uncapped `UploadHttp` client instead. Model
info/upload/rollback and `restart_ros` already do. **Scan (30 s), connect (60 s), launch
start/stop (90 s) and save-defaults (30 s) still do not, and are silently capped at 10 s.**

The app is no longer a thin subset of the web dashboard — it is now a superset. It consumes
~22 endpoints across both ports, six of which (`/api/slam/*`) the web dashboard does not
serve a UI for at all. That includes everything the older note listed as missing: LiDAR
(`/lidar_data`, drawn by `Controls/LidarView.cs`), live parameter tuning (`/api/get_param`,
`/api/set_param`, `/api/save_defaults` — `ParametersDrawer.xaml`), the data logger
(`/api/logger/*`, its own route) and IMU calibration (`/api/calibrate_imu`). What genuinely
remains web-dashboard-only is **record/playback** (`/api/record_playback`, `/teach`) — the
request model exists in `Models/DashboardApiModels.cs` and `ApiClient` can call it, but no
view-model does — and the competition reset (`/api/reset_competition`, same situation).

**The Map page (`Route.Slam`) replaces RViz on a second laptop.** It draws the live
`slam_toolbox` occupancy grid, with Save Map / Pause / Restart Mapping. The transport is
worth knowing: `dashboard.py` encodes the grid as a greyscale PNG using nothing but `zlib`
and `struct` (the same 300×300 grid is ~250 KB as a JSON int array and 5–20 KB as a PNG),
and the app decodes it through the same `BitmapImage` path the MJPEG reader uses. Polling is
two-tier — `/api/slam/status` every second, and `map.png` only when its `map_seq` moves, so
a parked robot costs one small GET per second. `Controls/MapView.cs` renders it, letterboxed,
with `NearestNeighbor` scaling.

Two traps live in that chain. `OccupancyGrid` is row-major from the **bottom-left** origin
while PNG rows run top-down, so `_render_map_png` emits rows in reverse — get it wrong and
the map is vertically mirrored, which looks plausible until the robot moves. And every
`/api/slam/*` service call must go through `_param_helper_node` on its own
`SingleThreadedExecutor`, never the dashboard node: these run on HTTP handler threads and
calling onto the `MultiThreadedExecutor` from there can deadlock. Save/restart/pause also go
through `UploadHttp`, since a ROS service call plus spin-wait outruns the 10 s ceiling.

**Restart Mapping is not a service call**, and this is the part that breaks silently. The
slam_toolbox on this robot advertises `save_map`, `pause_new_measurements`,
`serialize_map`/`deserialize_map` and `clear_changes` — **but no reset**, and nothing else
clears the pose graph in place. So `_slam_restart` finds the `async_slam_toolbox_node` PID by
scanning `/proc`, sends it `SIGINT`, and waits for a *different* PID to appear. That only
works because `bringup.launch.py` sets `respawn=True, respawn_delay=2.0` on that node —
**drop the respawn and Restart Mapping becomes Stop Mapping**, with the node staying dead
until the next full launch. The endpoint verifies the new PID rather than assuming it, so the
failure surfaces as an error naming `respawn` instead of a map that quietly never updates.
`/api/slam/status` reports `restart_supported` so the button is disabled up front rather than
offered and then failing.

Model management lives on the Settings page (`ModelViewModel` + the `ModelCard` block in
`SettingsView.xaml`, whose DataContext is assigned in code-behind). It uploads a BPU `.bin`
to the robot, keeps the displaced model as a `.bak`, can roll back, and nags when a model is
on disk but not yet loaded — `dnn.load()` runs once in `SignageDetector.__init__`, so a new
model does nothing until the stack restarts.

Layout convention: pages whose content is width-capped (`SettingsView` 640px,
`ControlsView` 820px) are `HorizontalAlignment="Center"`, not `Left` — capping the measure
and then pinning it left just leaves the window lopsided. `LogsView` and `DataLoggerView`
are uncapped and stretch.

## Conventions and traps

- ROS nodes are single-file, Python, `rclpy`, one `main()` per file registered in the
  package's `setup.py` `console_scripts`. A new node needs an entry there **and** in the
  launch file, or it just won't exist after a build.
- Launch files delay perception nodes ~3 s and `auto_driver` ~5 s so the camera is publishing
  first. Preserve that ordering when adding nodes.
- FastRTPS shared memory is disabled via `config/disable_shm.xml` (set as
  `FASTRTPS_DEFAULT_PROFILES_FILE` in the launch file) to avoid `/dev/shm` corruption.
- `obstacle_avoidance` floods the logs with WARNs while the robot is parked — filter before
  grepping.
- Restarting `risabot.service` can briefly drop the SSH session; it comes back.
- `git checkout`/`pull` only from inside `~/risabotcar_ws/src/RISA-bot`, never the workspace
  root.
- **`signage_detector.py` identifies signs by class *index*, not by name** — `class_ids != 9`
  to drop one, `(6, 7, 8)` for the traffic-light re-check, `1` for the hill. A model trained
  with its classes in a different order loads without complaint and acts on the wrong signs.
  No validation can catch this; it is why the upload UI states it in prose.
- The RDK X5 BPU toolchain (`hb_mapper`) is **amd64-only**, so model conversion can never run
  on the ARM64 robot. Compile on the PC in Docker, then upload.
- WPF implicit usings do **not** include `System.IO` or `System.Net.Http` — add them
  explicitly.
- In WPF, `Storyboard.TargetName` cannot be used inside a `Style` (a Style has no name scope,
  MC4011). Target the property path instead, e.g.
  `(UIElement.RenderTransform).(TranslateTransform.Y)`.
- A `DoubleAnimation` that has run with `FillBehavior.HoldEnd` outranks both bindings and
  Setters on that property afterwards. A `RepeatBehavior="Forever"` storyboard started in a
  `DataTrigger.EnterActions` needs a matching `StopStoryboard` in `ExitActions`.
